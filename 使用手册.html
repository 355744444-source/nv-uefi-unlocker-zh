导新手先看这页

如果这是你第一次接触这个工具，不必从第 01 章顺序读到底。这一节给出三条最该先记住的判断、一张推进路径图、 术语与常见误解速查，以及从零到跑通的最短清单。

0.1 先记住三条判断

判断一
它是「易失性」解锁
断电、冷启动、休眠恢复都可能清掉。不是刷 VBIOS，也不能一次搞定长期有效。
判断二
按芯片家族走，不按型号名
决定成败的是 PCI device ID 落在哪个段，同族共用资产。型号名只用于对照实测记录。
判断三
EFI 成功 ≠ 系统内有效
必须在系统内读回 SS 覆盖值才能算完成。日志全绿但性能没动，通常是被驱动或电源管理冲掉了。

0.2 推进路径与阶段验收点

0.3 术语速查

术语简要说明为什么对你有用
家族 / family按芯片分三组：tu10x（Turing，GTX 16 与 RTX 20）、ga102（Ampere GA10x，RTX 30）、ad102（Ada，RTX 40）固件资产按家族打包。选错家族，U 盘里的文件就是另一代卡用的，事务会直接失败
BDFPCI 总线地址，形如 01:00.0 或 0000:01:00.0多卡机器必须靠它指定目标卡；诊断工具也用它定位，不接受手填物理地址
PLM受保护的寄存器写权限门。主机不能直接改写受保护覆盖值解锁的本质是把门打开、写值、再交出去。门关着就意味着写不进去
FEAT / SS0 / SS1速率覆盖寄存器组（Turing 在 0x4096xx 段）。SS0=0x88888888、SS1 低 4 位 0x8 是「覆盖已生效」的读回特征值这是系统内唯一可信的成功判据。不看这个，只能靠感觉判断「好像快了」
Booter / V67 载荷NVIDIA 原厂签名的引导程序与执行载荷，经四写路径完成寄存器改写它们来自 NVIDIA 公开包并在本地再生，仓库不分发。这也是为什么要联网制盘
GSP-RMGPU System Processor 上运行的固件运行模式Turing 的 Windows 驱动必须处于 GSP 模式，否则会 TDR 循环或报 Code 43
RTD3 / D3cold运行时空闲断电，把 GPU 放到最深的省电状态Linux 上这是「日志全绿但没提升」的头号原因——断电就把易失解锁抹掉了
GOPUEFI 图形输出协议，负责启动阶段显示部分 AMI 固件在事务后的 GOP 重连阶段卡死，表现为黑屏而不是失败
SSDT / ESPEFI 系统分区（ESP）本工具默认不写 ESP、不改长期启动顺序。看到有人让你改 ESP，那不是官方流程
ssdiagWindows 侧系统内只读诊断工具，可临时加载签名驱动读寄存器它是 05 阶段的主力工具，默认只读，写操作要显式加 --reapply

0.4 常见误解

常见误解实际情况
「这是超频工具，能提高游戏帧数」解除的是 Tensor 计算发射速率的阉割，收益集中在 AI / 计算负载。游戏帧数不是目标，也可能毫无变化（见 01 章）
「刷一次就永久生效」完全易失。断电、冷启动、休眠恢复都可能清掉，每次冷启动要重放（见 04 章）
「RTX 50 系也能用，反正都是 NVIDIA」不支持。Blackwell 与 GA100 的引导链与本工具的事务家族不同（见 03 章）
「EFI 屏全绿就成功了」只证明事务路径跑完。必须在系统内读回 SS 值，两者要分开汇报（见 07 章）
「Secure Boot 可以留着，加个白名单就行」要么关掉，要么给 EFI 自签并让固件信任它。诊断工具内嵌的驱动在 Secure Boot 开启时也会被拒绝加载
「失败了一次，再跑一遍就好」同一个会话内不要重试。固件可能仍在运行、DMA 缓冲仍被占用，必须彻底断电后重来（见 08 章）
「把文件塞到内置硬盘分区，开机自动解锁」技术可行但属于自担风险的专业操作，官方不提供自动化脚本。默认交付形态是 U 盘 / 一次性启动菜单

0.5 最短路径清单

前提：你已确认显卡在支持范围内。下面五步只为「第一次跑通」服务，细节见后续各章。

  • 查身份：在目标机执行 nvidia-smi --query-gpu=name,pci.device_id --format=csv，或设备管理器看硬件 ID 里的 DEV_xxxx。
  • 关 Secure Boot：进固件设置关闭，或在自签信任链里放行 EFI。同时关闭「快速启动」，避免关机走休眠路径。
  • 制盘：在目标机解压目录运行 make-usbroot.ps1，让它自己识别代际，不要手猜 -Family。
  • 抄文件：按脚本末尾 expected 清单复制到 FAT32 U 盘根目录，BOOTX64.EFI 放 EFI/BOOT/。
  • 跑事务：一次性启动菜单选 U 盘 → 版本屏按空格 → 自动链回系统 → 跑 ssdiag 看 SS0/SS1。
先把基线记下来

在解锁之前，用固定负载（张量形状、精度、批次大小、功耗设置）跑一次并记录结果。解锁后再跑同一负载。 没有基线的「感觉快了」无法作为验收，也没法判断收益是否被功耗墙吃掉。

01这是什么工具

一句话：它在 NVIDIA 驱动加载之前，于 UEFI 阶段执行一段原厂签名的固件引导链，把消费级 GeForce 上有意限速的 Tensor 计算发射速率放开，然后交棒给操作系统。不刷 VBIOS，不改硬件，断电即复原。

1.1 它解决的问题

NVIDIA 在消费级 GeForce 上对 Tensor 计算吞吐做了限制，同一块硅在专业卡上能跑满，在 GeForce 上只能跑一部分。 这个限制不在你的驱动设置里，也不在 VBIOS 的可写区域里，而是由受保护的寄存器在初始化阶段决定。

工具的做法是：抢在驱动之前，用 NVIDIA 自己的签名固件链把权限打开，写入速率覆盖值，读回确认，再把原厂签名状态恢复并交棒系统。 因为写入发生在每次上电的初始化过程中，所以掉电即失效，不会留下永久改动。

1.3 明确不支持的情况

  • Pascal 及更早（GTX 10 系及以前）：没有对应的事务路径。
  • GA100（A100 0x20b0 / 0x20c2、A30 0x20f1）：不在支持路径中。
  • Hopper / Blackwell（含 RTX 50 系）：引导链与事务家族不同。

支持家族内的移动版、工作站版、CMP 矿卡与魔改卡，走所属家族的同一条路径——它们共用 Booter 与载荷资产。

制盘与运行都按 PCI device ID 落在哪个段来决定用哪套资产。型号名只用于对照实测记录，不参与路由决策。

两个容易踩的细节

GA102 实际收口到 0x2200..0x223f。旧版段尾 0x22..ff 经查已无 GA102 核心，只剩音频功能与 ARM 块，因此运行时段被收窄； 制盘脚本的白名单仍按 0x22xx 全段判断。两者不冲突，但看文档时别以为是笔误。

同族新 ID 会自动放行。未单列的 device ID 继承所属家族的证据等级，所以「我的 4070 变体没在表里」不等于不能用， 只等于没人给它单独做过记录。

2.3 多卡机器怎么指定目标

默认行为是处理所有受支持的卡，已解锁或不支持的卡跳过，单卡失败就走失败路径、不重试该卡。只想动其中一张时， 必须在 U 盘根放一个 tx-select-bdf.txt，内容写实际 BDF：

tx-select-bdf.txt
01:00.0
# 或完整形式 0000:01:00.0 —— 解析失败或目标缺失时会中止，不会退而求其次去动别的卡

BDF 必须来自现场清点（Windows 看设备管理器「位置」或 nvidia-smi --query-gpu=pci.bus_id，Linux 用 lspci -nn）， 不要照抄别人的示例。

3.2 证据等级怎么读

等级含义
✅本工具有实机证据。如果只有 EFI 成功、或只有系统侧验证，原文会单独注明——两种情况不等价
🟢上游或社区有同链硅验证，不等于本工具在该型号上逐卡验证过
🟡代码路径存在，完整实机验证待补充。可以用，但要自己承担首跑风险并回传日志
❌不支持
「device ID 能进事务路径」≠「该型号已实测」

这是读兼容性表最容易混淆的一点。路由只按 device ID 段判断，任何落在段内的卡都会被处理； 表里的等级说的是有没有人拿这块卡跑通并把证据归档。你的型号是 🟢 不代表会失败，只代表没人给它单独记录过。

04前置条件与风险

4.1 必需条件

  • UEFI 启动：目标机必须以 UEFI 模式引导，不能是 legacy/CSM 引导（CSM 关闭是多数成功案例的共同点）。
  • Secure Boot 关闭，或为 EFI 自签并让固件信任该证书。二者必须满足其一。
  • 一个 FAT32 U 盘，里面原有文件先备份——制盘要占用根目录和 EFI/BOOT/。
  • 入口时 GPU 有电并完成初始化：D3cold 状态下 BAR0 全为 0xffffffff，读不到寄存器，事务没法开始。
  • Turing 额外条件：Windows 侧 GSP 固件必须已运行（见 4.3）。

4.2 入口状态决定成败

进入 U 盘时的状态能否运行处理方式
独显直连，GPU 有电且已初始化可以运行首选形态。进入系统后仍需验证，不能只凭 EFI 成功
混合输出，dGPU 有电且寄存器可读可以尝试核对交棒前后状态；部分无 MUX 平台会出现「进系统无收益」
dGPU 处于 D3cold，BAR0 全 0xffffffff无法读取换一条能给 dGPU 上电并初始化的启动路径。工具不能通过 ACPI _PS0 / PR3 给完全断电的卡上电
休眠恢复 / D3 门控入口不可靠优先走「重启」而不是「关机」（关机会走快速启动的休眠路径）；不要仅凭 EFI 成功判断系统内仍有效

4.3 Turing（20 / 16 系）的 GSP 前置

Turing 的 Windows 驱动必须运行在 GSP 模式下，否则 legacy 初始化可能在被解锁的卡上 TDR 循环或报 Code 43。 在目标 Windows 的管理员 PowerShell 中执行一次，然后重启：

管理员 PowerShell · 目标机
PS> .\enable-turing-unlock.ps1

# 撤销该设置（如需）
PS> .\enable-turing-unlock.ps1 -Remove

# 重启后确认：EnableGpuFirmware=1，且 GSP 固件版本不是 N/A
PS> nvidia-smi -q | Select-String -Pattern "GSP|Firmware"
三条容易忽略的限制

必须重启。休眠恢复不会重新初始化驱动，改完不重启等于没改。

脚本只服务 Turing。它只给 Turing 显示设备设 EnableGpuFirmware=1。30 / 40 系不需要、也不应该开这个开关——已有一例 3080 20GB 魔改卡因此被 devinit 打回厂值。

Linux 不要跑这个脚本。Linux 走 GSP-RM 运行态检查：专有驱动 545+ 默认启用，但可能被 NVreg_EnableGpuFirmware=0 关掉，以实际运行态为准。

4.4 风险清单

这些是真实的代价，不是免责声明套话

关闭 Secure Boot 会降低整机启动链的安全性。它保护的是「谁能在我开机时运行代码」。为了跑一次解锁而长期关着， 等于长期放弃这层保护。用完请恢复原状。

解锁是易失的，但操作不是无风险的。黑屏、事务失败、驱动异常本身不能证明硬件永久损坏，也不能代替恢复后的设备检查。 若事务中途卡死且在同一会话内反复重试，固件可能仍在运行、DMA 缓冲仍被占用，风险会叠加。

与超频组合会突破原厂功耗与温度包络。发射率放开后功耗上升，散热与供电余量不足时可能触发热限甚至硬件损伤，由使用者承担。

这不是官方支持的功能。它依赖对未公开寄存器的逆向理解，厂商驱动更新可能随时改变行为（参见 TU106 新驱动的 FLR 复位问题）。

风险项可能性缓解办法
Secure Boot 长期关闭必然只在需要时关；完成后恢复开启，或改用自签 + 信任的窄化方案
事务后黑屏 / 卡死部分 AMI 平台常见放 no-reconnect.txt 跳过 GOP 重连；彻底断电后重来，不要同会话重试
驱动加载异常（Code 43 / TDR）Turing 未开 GSP 时高发先做 GSP 前置并重启；必要时 DDU 重装驱动
进系统后无收益混合输出 / RTD3 平台先用 ssdiag 读回判断是「被冲回」还是「本来就没写进去」，再对症处理
性能提升不及预期常见先确认撞功耗墙：观察 Board Power、Hot Spot 与限频原因

06启动、事务与交棒

6.1 进入方式

  1. 从系统里选「重启」，然后进固件的一次性启动菜单（通常 F12 / F11 / F8，视厂商而定），选 U 盘。 不要用「关机再开机」，因为快速启动会让关机实际走休眠路径。
  2. 笔记本优先切到独显直连。混合输出可以试，但要多核对一次交棒前后状态。

6.2 版本屏的按键语义

只有空格或回车会继续

版本屏显示后，按空格或回车才执行事务。其他任何键、或 30 秒不操作，都会中止事务并交回系统引导器—— 这是刻意的安全设计，不是超时 bug。中止时没有 GPU 写入。

事务执行期间，目标 GPU 可能出现黑屏或冻结在最后一帧，属于正常现象：loader 会断开 GOP 句柄， 让系统引导器自己去重建显示。看到黑屏不要急着断电，先等它完成链回。

6.3 日志

所有阶段日志写在 U 盘根目录 loader.log，每行带 [+ms] 阶段计时前缀， 所以回显耗时与事务等待时间可以直接从日志里分开看。下次运行会覆盖它，每次跑完先另存一份。

关键行包括：

  • DMA-PATH / BRIDGE-BME：loader 为 GPU 上游桥开启 Bus Master 并读回，结束时还原。这两行是 0x89 类问题的第一现场。
  • SAMPLE 段：冷态寄存器采样值，可与上游的「寄存器冷值表」对照。
  • HANDOFF-OUT：交棒时的状态，要和系统侧读回结果对照看。
  • 家族判据行：Ada 的 marker / HALT、Ampere 的 PLM 翻转、Turing 的 FEAT 读回。

6.4 慢速控制台的处理

部分机器的 iGPU 控制台刷新慢到约 1 行/秒，一次事务的回显会拖到分钟级。官方给的解法是安静模式，而不是异步输出 （UEFI 引导服务是单线程的，GOP 文本渲染本身同步调用，异步提不了吞吐）：

U 盘根目录 · tx-quiet.txt
# 建一个空文件即可。console 只显示裁决行：
# banner / 确认 / 每卡目标与结果 / HANDOFF / FINAL / CHAIN
# loader.log 仍然逐行全量记录
# 事务期间画面停在最后一行属正常，不是卡死

与自动运行标记组合，就是全自动无人值守的快速跑法（见附录 B 的标记表）。

07系统内验证与修复

这一章是整份手册里最不能跳过的部分。EFI 打印全绿只证明事务路径跑完了， 真正的验收是「驱动加载之后，覆盖值还在不在、性能有没有变化」。

7.1 Windows：ssdiag

管理员 PowerShell · 发布包目录
# 默认只读诊断：dump 每块 NVIDIA 显示设备
PS> .\ssdiag-x86_64-windows.exe

# 只看平台门与发现的卡，不加载任何驱动（最安全的第一步）
PS> .\ssdiag-x86_64-windows.exe --dry-run

# 按 DeviceID 缩小范围（多卡机器）
PS> .\ssdiag-x86_64-windows.exe --select 2504

# 写操作：仅在 FEAT 门仍开时重写 SS0/SS1 并读回，不写 PLM
PS> .\ssdiag-x86_64-windows.exe --reapply

工具会自行从操作系统发现 BAR0，不接受手填物理地址，也会按需唤醒停泊的卡。它内嵌一个经哈希校验的 pmxdrv.sys：若机器上已有可用设备（例如 nvoc 部署的）就直接借用，不做任何服务改动；否则临时解出并在 SSDIAG_PMXDRV 这个自有服务名下加载，退出时（含所有退出路径）停止、删除服务并清理临时文件，不会在你的服务列表里留东西。

Secure Boot 也会挡住诊断工具

内嵌的 pmxdrv.sys 是 Intel/COMODO 交叉签名的（叶子证书 2018-10 签发，没有 Microsoft 根）， 在 Secure Boot 开启的机器上不符合任何 DSE 的例外条款，加载会被拒绝。所以「关 Secure Boot」不只是为 EFI，也是为诊断。 --dry-run 不加载驱动，可以先跑它确认平台门状态。

7.4 Linux 的头号陷阱：RTD3

「日志全绿，进系统却一点提升都没有」在 Linux 上最常见的原因不是解锁失败，而是运行时空闲断电把易失状态清掉了。 若发行版在 /usr/lib/modprobe.d/nvidia-runtimepm.conf 里启用了 NVreg_DynamicPowerManagement=0x02， 需要用同名文件在 /etc/modprobe.d/ 覆盖（先备份已有配置）：

Debian / Ubuntu
$ echo 'options nvidia NVreg_DynamicPowerManagement=0x00' | \
    sudo tee /etc/modprobe.d/nvidia-runtimepm.conf
$ sudo update-initramfs -u
# Fedora / RHEL: sudo dracut -f

重启后要检查生效值，而不是只看配置文件写没写对：

检查项命令预期
驱动参数生效值grep DynamicPowerManagement /proc/driver/nvidia/params0 或 0x00
合并后的配置modprobe -c | grep -i DynamicPowerManagement只剩一项 0x00（不同名文件的 options 会累加，注意冲突项）

已经被掉电清掉的解锁状态，改配置不会自己回来，必须重跑一次 U 盘事务。配置只负责「别再把状态清掉」。

7.5 性能对比怎么做

  • 先有基线。解锁前用固定张量形状、精度、批次大小和功耗设置跑一次并落盘。
  • 同条件复测。解锁后再跑一次完全相同的负载，只改解锁状态这一个变量。
  • 核验基准工具本身。确认输入张量非零、没有被编译期常量折叠掉——社区有过实例，上游 mmapeak 存在编译期零输入坍缩， 后来改用运行时随机化的 fork 才测准。用 FP32 平价做控制标定噪声。
  • 分开汇报。「固件执行成功」「系统存活」「性能变化」是三件事，不要合成一个「成功」。

8.2 恢复流程

同一个会话内不要重试

出现 STOP、异常或黑屏卡死时，固件可能仍在运行、DMA 缓冲可能仍被占用。此时再跑一次不是「重试」，是叠加风险。

  1. 彻底断电完全关机断电。笔记本按厂商流程做 EC 放电（长按电源键或拆电池，按机型手册来）。
  2. 拔 U 盘，正常启动走原有的系统引导项正常开机。本工具不需要写 ESP、也不改永久启动顺序，所以这一步不需要任何清理操作。
  3. 检查设备状态看设备管理器错误码与系统事件日志，保留 loader.log 原件，再按具体症状对照 8.1 排障。
  4. 驱动仍异常时再做一次彻底断电并检查；必要时用 DDU 重装驱动。

解锁效果会随断电清除。黑屏、事务失败或驱动错误本身不能证明硬件永久损坏，但也不能代替恢复后的设备检查。

8.3 常见问答

Q1能不能装到内置硬盘分区，开机自动解锁？

可以，但属于专业用户自担操作，官方不提供自动化脚本。实证可行的形态是：从数据卷缩出约 2 GB 的 FAT32 分区， 按 U 盘同款布局放置 EFI 与资产，在 BIOS 启动菜单里把它（通常显示为 UEFI OS）手动调到前面，或用 F12 一次性选择。 随时可以从 BIOS 菜单改回 Windows Boot Manager，不刷任何东西。

走不通的路要说清楚：用 bcdedit /create /application osloader 造条目，device 落在盘符上、重启即失效； bootsector 类型的 device 字段是空的——两条路都进不了 {fwbootmgr}。别在这上面花时间。

官方不做自动化的理由很实在：缩容场景千差万别（双系统、跨盘引导、btrfs / zfs 不支持在线缩容）， 强行覆盖所有存储拓扑有真实的数据安全风险。

Q2为什么事务成功后还会复位或黑屏？

部分 AMI 固件会在 GPU 事务完成后的 GOP 重连中卡死或复位。loader 对断开后仍存在的无路径 GOP 使用非递归的厂商重连， 并在链式加载前跳过 NVIDIA 显示功能。

若仍停在 RECONNECT: ConnectController ... begin 或该阶段复位，断电恢复后在 U 盘根放 no-reconnect.txt 跳过目标 GPU 重连。Windows Boot Manager 可以自行建立控制台，跳过重连不等于跳过系统内验证。

Q3SVM / VT-x / VT-d 要不要关？

在已验证平台上不需要关。任务管理器里那个「虚拟化」不是 PCI Command 的 Bus Master 位，两者别混。 个别 AMD 平台的失败来自 BIOS 的 IOMMU（AMD-Vi）挡住了 booter 的 DMA，关掉相关选项后全链通过——但那属于平台侧的 DMA 前提问题， 处理依据是日志里的桥 BME 行，不是盲目关虚拟化。

Q4回放模式和只读检查有什么区别？

移除 v67-*.bin 会进入回放模式：不执行解锁载荷，但仍会断开驱动、执行签名固件并可能复位 GPU。 它不是只读检查。真正的只读采样要用 cargo efi 构建的程序（不带 tx feature）。

Q5失败了怎么反馈才有用？

提交完整 loader.log、GPU 型号与 PCI ID、平台、驱动版本、显示模式、进入方式、系统侧诊断结果。 魔改卡另附原型号、VBIOS 与显存容量。日志可以先脱敏机器信息。性能问题要附相同条件下的测试规模、精度、功耗和前后结果。

超频 / 频率控制需自行确认散热与供电余量

推荐顺序：

  1. 先独立验证本工具完成解锁、在系统内确认状态、记录基线。这一步没确认之前不要叠加任何超频变量。
  2. 再按 nvoc 文档选控制方式不要照搬别人的极限参数——那通常是特定卡 + 特定散热的实验值。
  3. 同负载对比用 cli-stressor-cuda-rs 在相同负载下比较，同时监控 Board Power、Hot Spot 和限频原因。
叠加后的功耗温度可能远超原厂包络

超功耗、超压、超温造成的物理损坏由使用者承担。见到「别人 4090 跑 600W」这类数字时记住： 那是别人的卡、别人的散热、别人的风险预算。

10源码构建

用发布包就够用了，这一章只在你需要改代码、或者想自己出 BOOTX64.EFI 时才需要。

10.1 两个构建目标，能力完全不同

命令产物能不能解锁
cargo efitarget/x86_64-unknown-uefi/release/loader.efi不能。这是只读采样程序，用于诊断
cargo efi-tx同上路径，但带 --features tx能。这是带 GPU 写路径的事务程序
cargo build --release宿主侧 assets 与 sim—　不含 loader
cargo xt宿主测试（--workspace --exclude loader）—
这是最容易搞错的一处

很多人照着 README 敲 cargo efi，拿到 loader.efi 放进 U 盘，结果什么都没发生。 因为 cargo efi 是只读的。要能写，必须用 cargo efi-tx。

另外不要对宿主目标执行 cargo build --workspace——loader 是 UEFI 目标，编不了宿主三元组。

10.2 完整构建流程

Rust 工具链（Windows 选 MSVC 版）· 仓库根目录
# 1. 加 UEFI 目标
$ rustup target add x86_64-unknown-uefi

# 2. 宿主侧工具（assets / sim）
$ cargo build --release

# 3. 事务版 EFI 应用（★ 注意是 efi-tx，不是 efi）
$ cargo efi-tx

# 4. 用自建产物制盘
PS> .\release\make-usbroot.ps1 -Family 40 `
      -AssetsExe .\target\release\assets.exe `
      -BootEfi .\target\x86_64-unknown-uefi\release\loader.efi
Linux 等价写法
$ bash release/make-usbroot.sh --family 40 \
    --assets ./target/release/assets \
    --boot-efi ./target/x86_64-unknown-uefi/release/loader.efi

ssdiag 是独立的 crate，不在发布包里的情况下单独构建：

Windows
PS> cargo build --release --manifest-path tools/ssdiag/Cargo.toml

11安全边界与已知缺口

上游把「做不到」和「没验证」写得比「做到了」更明确。这一章照抄它的边界，因为知道边界在哪，比相信工具万能更有用。

11.1 设计纪律

  • 写入以读回为验收依据。状态码和「运行完成」提示不构成独立执行证明。
  • 异常后同会话不重试；只从 U 盘 / 一次性启动菜单进入，不覆写系统 ESP，不设置常驻 BootOrder。
  • NVIDIA 固件从钉版输入本地生成，不分发、不入 git；校验失败即停止。
  • 模拟器再全绿，真机验收仍以读回为准。

11.2 明确写出的缺口

缺口影响
loader 只记录 PROM CRC32尚未实现逐卡 ROM/PROM SHA-256 强制匹配，所以不要声称它做过这件事
描述符解析支持 V2/V3V1 未实现，encrypted 位未保留或强制检查
运行装载使用 portalFalcon DMA 仍属实验代码
模拟器部分 verdict 来自故障开关与模拟侧 marker不能替代真机读回
WPR2 守卫、pre-FLR 与家族路径相关不能把所有拒绝都称为「零写」。界面中止、严格 D0 入口中止才有零写语义；EBUSY 之前可能已修改 PCI 配置并断开控制台
Ada 的 FBPA 读回 0xffffff0f这是允许的观察值，不应单独据此判失败。scrubber 的 handoff/超时警告也不是最终判据

BU 盘文件与标记速查

B.1 必需文件

见 5.5 家族文件清单。要点重复一次：只复制脚本 expected 清单里的文件， 中间文件不要放上去；EFI/BOOT/BOOTX64.EFI 替换前先备份。

B.2 可选标记文件（放 U 盘根，普通使用不需要）

标记文件行为
tx-require-d0.txt入口非 D0 时中止，不进行 GPU 写入或复位。想要「宁可不动」时用它
tx-select-bdf.txt内容为 bb:dd.f 或 dddd:bb:dd.f，只处理匹配的卡；解析失败或目标缺失时不会改选其他卡
chain-target.txt第一个非空、非 # 行指定优先 EFI 路径，逐卷查找；找不到时记日志并回退默认顺序
tx-no-preload.txt禁用预驱动预载链回，回到事务后逐卷扫描的旧路径
no-reconnect.txt跳过目标 GPU 的 GOP 重连。适用于事务后重连卡死或复位
i_know_what_i_am_doing.txtN 秒倒计时后自动运行，任意键中止；首行数字（1–30）可覆盖秒数，缺省 5
tx-flush-lines.txt日志 flush 频率，首行数字 0–4096 覆盖（缺省 16 行/次；0 = 仅阶段标记行）。调大减少 U 盘慢写停顿，代价是挂死时丢更多日志尾巴
tx-quiet.txt安静模式：console 只显示裁决行，loader.log 仍全量记录
tx-gop-disconnect.txt诊断开关：断开所有 GOP 句柄（含 iGPU）。不要当提速手段用——console 静默后无增益，且其他卡的 console 被杀后 loader 不会恢复
关于自动运行标记

i_know_what_i_am_doing.txt 会让事务在倒计时后自动执行——这等于放弃了「必须人工确认」这层保护。 正常部署时应当确保这个文件不存在。它只用于明确要求的无人值守场景。
